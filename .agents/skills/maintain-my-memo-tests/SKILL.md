# my-memoのテストを保守する

利用者またはデータ整合性に影響する、アプリが所有するふるまいを保護する。コードを変更したという理由だけでテストを追加しない。

## 契約から検討を始める

1. テストを書く前に、変更対象のアプリケーションコードと周辺テストを確認する。
2. 退行する可能性があるアプリ固有の契約を明示する。
3. より下位の安定したテストが、同じ契約をすでに保護していないか確認する。
4. 意味のあるアプリの不具合を検出できる場合だけ、テストを追加または変更する。

次の項目を優先する。

- 認可と所有者分離
- 破壊操作と関連データの整合性
- クォータ境界、並行処理、予約、および部分失敗後の補償処理
- 入力上限と危険な入力
- 入力保持、エラー通知、二重送信防止、および失敗後に再操作可能な状態へ戻ること
- アクセシブル名、フォーカス移動、現在地、操作可否、および遷移先
- 許可するURLスキームや出力属性など、アプリが定めたセキュリティ方針

次の内容はテストしない。

- Chromium、Workers、Hono、daisyUI、Markdownライブラリなどが、ドキュメントどおり動くこと
- CSSユーティリティやコンポーネントのクラス名
- 親子DOM構造、SVG個数、レイアウト配置。ただし構造自体がアクセシビリティ契約である場合を除く
- 明示的なプロダクト要件がない、依存ライブラリの構文網羅、性能、壊れた入力への耐性
- 焦点の合った下位テストがすでに保護しているふるまい

依存先との境界にアプリ独自の方針が含まれる場合は、その方針をテストする。例として、サムネイルの寸法上限、Object URLの解放、MarkdownのURL許可リスト、レスポンスヘッダー、R2とD1の補償処理がある。

## テスト分類を一つだけ選ぶ

次のファイル名規約を使用する。

- `*.test.ts`: D1、R2、HTTPルーティング、SSR、実ブラウザを必要としない、純粋または決定的なアプリロジック。`pnpm run test:unit` で実行する。
- `*.integration.test.ts` または `*.integration.test.tsx`: Workers、D1、R2、HTTPルート、マイグレーション、SSRの結合。`pnpm run test:integration` で実行する。
- `*.browser.test.tsx`: Chromiumを必要とする、アプリ固有のUI動作。`pnpm run test:browser` で実行する。

`import.meta.vitest` は使用しない。収集漏れを可視化するため、テストは専用ファイルへ置く。

テストファイルを `app/islands` に置かない。HonoXがproduction用islandエントリとして扱う可能性がある。islandのブラウザテストは `app/tests/browser` に置き、`@/islands/...` から対象を読み込む。テスト配置を変更した後は、production manifestにテストbundleが含まれていないことを確認する。

## 安定したアサーションを書く

- `describe` とテストケースの名前は日本語で記述し、保護する仕様が分かるようにする。
- 並行処理、時刻境界、バイナリfixture、分かりにくい補償処理には、短い理由コメントを残す。
- ロール、アクセシブル名、ラベル、表示メッセージ、値、URL、フォーカス、無効状態、DB状態、保存オブジェクトの状態を優先して検証する。
- アプリが要素をDOMから削除する場合は `not.toBeInTheDocument()` を使用する。
- 実用上問題がなければ、mockの呼び出し詳細ではなく、アプリの最終結果を検証する。
- 破壊操作や所有者に依存するルートでは、該当する分岐について、未認証、別所有者、所有者による成功、存在しない対象、関連データの結果を確認する。
- 複数システムへ書き込む処理では、成功経路に加え、重要な各失敗境界で後始末されることを確認する。

## 収集に関する不変条件を守る

次のリポジトリファイルを唯一の実装として扱い、このSkill内へ実装を複製しない。

- `vitest.unit.config.ts`
- `vitest.config.ts`
- `vitest.browser.config.ts`
- `scripts/check-test-collection.mjs`
- `package.json`

`app/**` 配下のすべてのテストファイルが、いずれか一つの設定だけに収集される状態を保つ。ファイル名、ディレクトリ、Vitest設定を変更した場合は `pnpm run test:collect` を実行する。未収集、複数分類、想定外の収集、空の分類が見つかった場合は、ガードを回避せず原因を修正する。

## 変更量に応じて検証する

実装中は、影響を受ける最小のテスト分類から実行する。引き渡し前に次を実行する。

```powershell
pnpm run test:collect
pnpm run test:all
pnpm exec tsc --noEmit
pnpm exec biome check app scripts vitest.config.ts vitest.unit.config.ts vitest.browser.config.ts package.json
pnpm run build
git diff --check
```

テスト配置またはHonoXのエントリディレクトリを変更した場合は、build後に `dist/.vite/manifest.json` を確認する。`.browser.test`、`.test`、テスト専用chunkを含めない。

削除、統合、書換、追加したテストを、影響するアプリ固有の契約ごとに報告する。テスト件数の増加やカバレッジ率を、テスト品質の根拠にしない。
